# my-service-agent — 반품·교환 안내 챗봇 설계

> 작성: Sung, Hyun-Joon · 2026-10-12
> 아이펠 프롬프트 엔지니어링 4. [프로젝트] 도구 설계 — 에이전트에게 무엇을 줄 것인가

## 서비스 소개

온라인 쇼핑몰 고객의 반품·교환 문의를 안내하는 챗봇이다. 정책을 찾아 설명하고, 고객이 준 주문번호로 반품·교환 가능 여부를 확인하며, 고객이 최종 확인하면 요청을 접수한다. 환불 금액 확정, 정책 예외, 접수 취소는 챗봇이 결정하지 않고 담당자에게 넘긴다.

이 저장소는 구현이 아니라 **설계**다. 어떤 도구를 주고, 어디서 멈추고, 무엇을 기록할지를 정했다. 설계 근거는 직접 돌려 본 실습 기록(`my-agent/traces/`)이다.

## 폴더 구조

```
my-service-agent/
├── README.md              # 이 문서: 서비스 소개, 설계 결정 요약, 실행하지 않은 것과 이유
├── design-packet.md       # 설계 패킷 7항목 (시스템 지시, 도구 계약 4개, 권한, 오류·이관, 반환 형식, 테스트 8문항, 트레이스 양식)
└── my-agent/              # 실습 1·2 산출물
    ├── tool-definition.md # get_inventory 도구 정의서와 실패 사례 보완
    ├── show_injection.py  # 도구 설명이 모델 입력에 들어가는 모습 확인 (토큰 289 / 288 비교)
    ├── inventory_tool.py  # 재고 조회 도구: 모델 요청 → 하네스 실행 → 최종 답
    └── traces/            # 실행 기록 원문
        ├── trace-01.txt   # 정상: BUSAN-02 재고 조회 성공
        ├── trace-02.txt   # 실패: "부산 3번"을 되묻지 않고 BUSAN-02로 바꿔 조회
        ├── trace-03.txt   # 실패 지속: 설명서에 되묻기 규칙을 넣어도 같은 결과
        ├── trace-04.txt   # Claude Code + Qdrant MCP: 설정 파일을 확인해 collection_name 결정
        └── trace-05.txt   # opencode + Qdrant MCP: collection_name을 지어냄
```

## 실습에서 관찰한 것 (설계의 근거)

| 기록 | 관찰 | 설계에 반영한 곳 |
|---|---|---|
| trace-02 | 목록에 없는 창고("부산 3번")를 모델이 되묻지 않고 허용 코드 BUSAN-02로 바꿨다. 허용 코드라 하네스 검사를 통과해 다른 창고 재고가 정답처럼 전달됐다 | 모든 도구의 "안 쓰는 때"에 "정보가 없거나 애매하면 묻는다" 명시 |
| trace-03 | 도구 설명에 "확실하지 않으면 호출하지 말고 되물어라"를 넣어도 결과가 같았다 | 지시문에만 기대지 않고 **하네스 검사**로 막음 (주문번호는 고객이 말한 값과 같아야 실행) |
| trace-04, 05 | 기본값이 없는 인자(collection_name)를 Claude Code는 설정을 읽고 채웠고, opencode 모델은 실행마다 다른 이름으로 지어냈다 | 모델이 짐작할 수 있는 자유 입력 칸을 줄임: 형식이 정해진 order_id, 선택지가 닫힌 type·reason |

## 설계 결정 요약

**도구를 네 개만 둔 이유.** 반품·교환 안내에 꼭 필요한 동작은 정책 찾기, 주문 확인, 가능 여부 판정, 접수 네 가지다. 판정을 주문 조회와 분리한 것은 "배송 완료 후 7일" 같은 날짜 계산을 모델이 하면 틀릴 수 있어서, 계산은 프로그램이 하고 모델은 결과(eligible, 근거 조항)만 전달하게 하려는 것이다. 환불 금액 계산이나 접수 취소 도구는 일부러 만들지 않았다. 도구가 없으면 모델이 그 일을 시도할 수도 없다.

**권한을 나눈 기준.** 상태를 읽기만 하는 도구 셋과 상태를 바꾸는 도구 하나(create_return_request)로 나눴다. 쓰기 도구는 판정 통과와 고객의 명시적 확인이 모두 있어야 실행되고, 이 조건은 모델의 판단이 아니라 하네스가 confirm_token으로 검사한다. 개인정보가 담긴 주문 조회는 읽기지만 본인 주문만 조회되도록 하네스가 소유자를 검사한다.

**실패 뒤 행동을 이렇게 정한 근거.** trace-02·03에서 작은 모델은 빈칸을 짐작으로 채웠고, 지시문을 고쳐도 고쳐지지 않았다. 그래서 정보가 모자라면 "묻기", 같은 오류가 반복되면 "담당자 이관", 정책 판단이 필요하면 "보류 후 이관"으로 행동을 하나씩 정했고, 같은 호출 3회 반복은 하네스가 루프를 끊게 했다. 재시도는 일시적 오류에 한해 1회만 허용해 같은 실수를 되풀이하지 않게 했다.

## 실행하지 않은 것과 이유

| 하지 않은 것 | 이유 | 다음에 측정할 지점 |
|---|---|---|
| 도구 4개의 실제 구현 | 과제 범위가 설계 문서까지다 | 구현 후 테스트 8문항을 돌려 trace 양식으로 통과/실패 기록 |
| 하네스 검사 코드(주문번호 일치, confirm_token) | 규칙만 정의했다. 실습에서 확인한 것은 지시문만으로는 짐작 대입이 막히지 않는다는 점까지다 | 4번(짐작 유도)·8번(공격) 문항이 실제로 차단되는지 |
| 정책 검색의 한국어 성능 확인 | 실습의 임베딩 모델(BAAI/bge-small-en-v1.5)은 영어용이다. 문장 3개로는 1위가 맞았지만 정책 문서가 늘면 순위가 틀릴 수 있다 | 정책 조항 수십 개에서 1번 문항의 검색 1위 정확도 |
| Qdrant 영구 저장 | 실습은 `:memory:`로 꺼지면 사라지는 설정이었다 | 저장 위치를 고정한 뒤 재시작 후에도 검색되는지 |
